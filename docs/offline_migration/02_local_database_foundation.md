## Objective

Establish the local SQLite database using the Drift ORM, including the `AppDatabase` class, schema versioning, migration support, foreign key activation, UUID storage as TEXT, financial storage policy, DAOs, the Riverpod database provider, transaction rules, code generation expectations, and database lifecycle.

## Current State

The application has no local database. All data is fetched from the FastAPI backend via Dio. The `decimal` package is used for financial values in Flutter entities. UUIDs are generated by PostgreSQL's `gen_random_uuid()` and transmitted as strings.

## Target State

- A Drift-based `AppDatabase` class providing access to SQLite.
- Tables for clients, projects, milestones, payments, and expenses.
- Foreign key enforcement enabled in SQLite.
- UUIDs stored as `TEXT` columns.
- Financial values stored as `TEXT` (string representation of `Decimal`), never as `REAL`.
- Schema versioning and migration support via Drift's migration framework.
- DAOs (Data Access Objects) for each entity.
- A Riverpod provider exposing the database instance.
- Transaction support for multi-table operations.
- Drift code generation configured.

## Data Model Impact

This phase creates the local database schema. See [data_model_mapping.md](data_model_mapping.md) for the full field-by-field mapping.

Key decisions:
- UUIDs stored as `TEXT` (not BLOB) for readability and compatibility.
- Financial values stored as `TEXT` representing `Decimal` strings (e.g., `"1250000.00"`).
- Dates stored as `TEXT` in ISO 8601 format (`YYYY-MM-DD`).
- Timestamps stored as `TEXT` in ISO 8601 format with timezone (`YYYY-MM-DDTHH:MM:SSZ`).
- Booleans stored as `INTEGER` (0 or 1) per SQLite convention.
- Enums stored as `TEXT` with the same string values used by the backend.

## Acceptance Criteria

1. `AppDatabase` opens and closes without errors.
2. All tables are created with correct columns and types.
3. Foreign keys are enforced (inserting a child with a non-existent parent fails).
4. Financial values stored as TEXT preserve Decimal precision.
5. DAOs provide basic CRUD operations for each entity.
6. `databaseProvider` is accessible via Riverpod.
7. `flutter analyze` reports zero errors.
8. All database tests pass.
9. Drift code generation succeeds without errors.

## Risks

See [risk_register.md](risk_register.md). Key risks:

- R-004: SQLite corruption — mitigated by WAL mode and proper close handling.
- R-008: Financial precision loss — mitigated by TEXT storage policy.
- R-012: Missing foreign-key enforcement — mitigated by explicit `PRAGMA foreign_keys = ON`.
- R-017: Release/debug differences — mitigated by testing both configurations.

## Rollback Strategy

If this phase fails or causes issues:

1. Remove Drift dependencies from `pubspec.yaml`.
2. Delete `frontend/lib/core/database/` directory.
3. Delete generated Drift files.
4. Revert `pubspec.yaml` to previous state.
5. The application returns to its Dio-based architecture unchanged.

This rollback is safe because no existing code depends on the database yet.
